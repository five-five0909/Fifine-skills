# 版本号升降级与定稿锁定

> 与 `scripts/naming_lib.py` 的 `VER` / `LOCKED_TAGS` 和 `scripts/apply_naming.py` 的
> `LOCKED-REFUSE` 判据对应。版本号**由你在方案里写死**，执行器只做校验与拒绝，不会二次计算。

## 1. 版本段语法

```python
VER = r"V[1-9]\d*(?:\.\d{1,2}){0,2}"     # V1 / V2 / V1.1 / V1.10
```

- 大写 `V`，前置下划线：`_V1`，不是 `-v1`、`v1`、`第1版`。
- 从 `V1` 起——`V0` 被正则拒绝（`[1-9]`）。「还没开始写」用 `【草稿】` 标签表达，不用 `V0`。
- 次版本支持两位数，所以 `V1.9` 的小改动是 `V1.10`，不会撞墙。
- 正则容忍最多两段小数（`V1.1.2` 也能通过），但约定只用主/次两段；出现三段通常意味着有人把构建号塞进了文件名，应收敛回两段。
- 版本号写在核心信息里会被抓到：`20260910_项目-需求-V1.2.pptx` **不合规**（点号落进关键词里，扩展名不再吞掉 `.2`），诊断为「版本号请写成 `_V` 前置下划线」；`20260910_项目-需求-V1.pptx` 里 `V1` 是合法关键词，因此仍能解析，只给一条警告并写明应改成 `_V1`。

## 2. 大改 / 小改的判据

| 变更 | 具体判据 | 动作 | 例 |
|---|---|---|---|
| 大改动 | 结构重编、方案更换、章节增删、结论反转、口径重算 | 主版本 +1，次版本归零 | `V1 → V2`，`V2.3 → V3` |
| 小改动 | 文字调整、格式微调、错别字、样式、图表美化 | 次版本 +1 | `V1 → V1.1`，`V1.1 → V1.2` |

判定由你完成，并在确认表的 `依据` 列写明理由（`小改：仅措辞与排版 → V1.1`）。用户说「重写了一遍」就是主版本 +1，别替他保守。

**不要复用已对外发出过的版本号**。`V3` 已经发给客户，就不能再拿 `V3` 表示更新的东西；从 `V2.1` 跳到 `V3` 是安全的。跳号（`V3 → V5`）允许，但要在 `依据` 列说明原因。

## 3. 迭代时哪些字段动、哪些不动

| 字段 | 定稿前的常规迭代 | 定稿后重启的新循环 |
|---|---|---|
| 状态标签 | 按实际进度换（草稿 → 待审 → 待改） | 新副本挂 `【待改】` |
| 日期 | **不动**，保持初版日期 | **改为今天** |
| 核心信息 | **不动**，一个字符都不要改 | **完全一致** |
| 版本号 | 按上表升 | 跳到 `n+1` |

理由：搜索与分组的唯一键是**核心信息**。同一份文档的各个版本必须共享同一段核心信息，否则搜不到齐；日期在定稿前保持初版值，是为了让 `_V1 _V2 _V3` 排在一起而不被时间轴打散。

定稿之后被要求继续改，属于**新一轮工作**，因此日期换成今天：

```
【定稿】20260918_秋季活动-报价单_V4.docx        ← 冻结，不动
【待改】20260925_秋季活动-报价单_V5.docx        ← 新副本，今天，核心信息一致
```

## 4. 定稿锁定

`LOCKED_TAGS = ("定稿", "归档")`。执行器读**源文件当前名字**里的标签：

```python
if tag in LOCKED_TAGS and stem_of(new_name) != stem_of(old_name):
    -> LOCKED-REFUSE：「定稿」已锁定，禁止改动主名；需要继续迭代请另存【待改】新副本
```

| 请求 | 结果 |
|---|---|
| 【定稿】改核心信息 / 改版本号 / 换标签 | `LOCKED-REFUSE` |
| 【定稿】只换目录，主名不变（同名纯移动） | **放行**——归档位移不破坏版本记录 |
| 【归档】任何主名改动 | `LOCKED-REFUSE`；归档语义上只读，位置可以变 |
| 【草稿】【待审】【待改】 | 正常改名，但版本号来源必须写在 `依据` 列 |

`--targets dirs` 时目录不参与锁定判断（目录本来就禁标签）。锁定判据只看名字里的标签，不检查文件内容——**没有**任何机制能发现「有人直接改了 Word 内部但没改名」，所以流程上定稿后要冻结分发副本。

## 5. 复制不是本 skill 的职责

`apply_naming.py` **只改名和移动，绝不复制、绝不删除、绝不覆盖**。所以第 3 节的「另存新副本」需要你先做实体复制（Word/WPS 的「另存为」，或 `shutil.copy2`），再把新文件按 `【待改】<今天>_核心_V(n+1).<ext>` 命名——命名这一步仍走 Step 4 确认门。

如果用户要求「保留原件并生成新版本」而你不打算真的复制文件，就不要提交任何 plan 条目：`old_path → new_name` 的改名会把原件搬走，那是**替换**，不是**加版本**。

## 6. 映射日志即版本台账

每次正式执行都写映射日志：

```json
{"generated_at": "...", "note": "", "created_dirs": [...],
 "moves": [{"old_path", "new_path", "intermediate", "status", "reason"}],
 "rejected": [{"index", "old_path", "new_name", "status", "reason"}]}
```

- `moves[].status == "OK"` 才是真的动了；`DRY-RUN` / `CONFLICT` / `ERROR` 都留在日志里可查。
- 被 `LOCKED-REFUSE` 拦下的条目进 `rejected`，**这是台账**：过几个月有人问「定稿为什么没被改乱」，答案在这些日志里。
- 日志建议与归档根放在一起长期保留（例如 `_整理日志/`），临时 plan 和 audit JSON 可删。
- `--undo <log>` 只回滚 `status == "OK"` 的条目，逆序执行；`created_dirs` 反向删除，非空则保留。回滚不会撤销你自己手工做的复制，也不会删除任何文件内容。
