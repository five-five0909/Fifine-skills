# 目录结构与日期适用范围

> 与 `scripts/naming_lib.py` 的 `DIR_RE` / `validate(kind="dir", depth=...)` / `STRUCTURAL_DIRS`
> 以及 `scripts/audit_names.py` 的 `ancestor_context()` 对应。

## 1. 三层骨架

```
秋季活动/                          ← 归档根（用户选定的整理边界，本身不参与命名）
├── 20260910_秋季活动-筹备/         ← 第一层：日期必填
│   ├── 需求文档/                  ← 第二层起：裸名，不带日期
│   ├── 交付物/
│   │   ├── 【草稿】20260912_秋季活动-报价单_V1.docx
│   │   └── 【定稿】20260918_秋季活动-报价单_V4.docx
│   └── 原始素材/
├── 20260928_秋季活动-复盘/
│   └── 交付物/
└── 20261007_部门-季度会议/         ← 同一根下可以并列多个项目
```

| 层 | 规则 | 例 |
|---|---|---|
| 归档根 | 用户给的整理边界。**脚本不评价、不改名**——它是所有相对路径与 `--depth` 的计算原点 | `~/Documents/秋季活动` |
| 第一层（`depth == 1`） | `YYYYMMDD_核心信息`，日期**必填** | `20260910_秋季活动-筹备` |
| 第二层起 | `核心信息`（1~5 关键词），日期**不要求** | `交付物`、`需求文档`、`原始素材` |

## 2. 为什么日期只在第一层必填

排序的目的只有一个：**让项目按时间自然排在前面**。日期写在第一层已经达成这个效果；往里每层都塞日期，只会：

- 让结构目录变得难以辨认（`20260912_交付物` 里的日期属于谁？属于目录还是里面最新的文件？）；
- 让结构目录在时间变化时必须改名，而它里面的文件是**引用路径**的——`src/` 里写死的资源路径、脚本里的相对路径都会断。

于是有了这条判据：`validate(kind="dir", depth=1)` 缺日期前缀即 `NON_CANONICAL`，`depth >= 2` 不带日期才是合规。`audit_names.py` 从根目录起算 `depth`，所以 `--depth` 也决定了这条规则被检查到哪一层。

**日期不该出现在结构目录上的另一个理由**：结构目录是长期存在的（下个月还有 `交付物/`），而日期是一次性的。二者混用会让「这个目录是什么时候的」变成一个没有答案的问题。

## 3. 目录禁止携带的东西

| 禁止 | 原因 |
|---|---|
| `【】` 状态标签 | 状态属于**单个交付物**的进度，目录同时容纳 `草稿` 和 `定稿` 两种状态，标签放目录上必假 |
| `_V` 版本号 | 版本随文件演进，目录版本会诱导人往里塞 `交付物_V1`、`交付物_V2` 两份重复目录 |
| 日期（第二层起） | 见上节 |

判据在 `validate()` 里是三条硬检查：`"【" in name or "】" in name` → 报错；`re.search(r"_V\d", name)` → 报错；`depth == 1` 且无日期 → 报错。

## 4. 结构目录的推荐名

`STRUCTURAL_DIRS` 是脚本认识的**角色目录名单**：它们不携带项目信息，所以向上找项目关键词时会被跳过。

- 过程与结果：`需求文档`、`过程稿`、`交付物`、`终稿`、`参考`
- 素材：`原始素材`、`图片`、`图表`、`数据`、`附件`
- 收纳：`收件箱`、`临时`、`其他`、`版本备份`、`归档`
- 英文等价：`output(s)` `inputs` `assets` `refs` `references` `data` `draft(s)` `final(s)` `archive` `misc` `other` `temp` `images` `figures` `tables` `src` `docs`

这份名单是**白名单式的启发**，不是封闭集合——新名字（`合同/`、`供应商/`）照样合规，只是不会被当作项目关键词来源。目录本身允许中英混排，但同一层里保持一种语言。

## 5. 项目关键词怎么来

`audit_names.py` 的 `ancestor_context()` 沿着相对路径向上走，取**最近一个**能匹配 `DIR_RE` 的上级目录名，拿它核心信息的**第一段**当项目关键词；同一次上溯还会顺手收集该目录的日期前缀作为 `ancestor_date`。向上过程中会跳过：归档根自己的名字（多半是个临时下载目录）、`EXCLUDED_DIRS`、以及 `STRUCTURAL_DIRS` 里的角色目录。

行为示例：

```
交付物/【草稿】20260912_报价单.docx
        ↑ 候选关键词只有「报价单」，项目段空缺
   → 向上跳过「交付物」（在 STRUCTURAL_DIRS 里）
   → 命中「20260910_秋季活动-筹备」，取第一段「秋季活动」
   → 建议名 20260910_秋季活动-报价单_V1.docx
```

因为项目段来自**目录名**，所以把项目目录命名好，等于给里面所有文件预置了核心信息的第一段。这是这套结构最省事的收益，也是为什么模式 B 里**先定目录、后定文件名**。

## 6. 移动与新建目录

plan 条目里的 `new_dir` 可以指向还不存在的目录，执行器会按 top→leaf 建齐并记入映射日志的 `created_dirs`；`--undo` 时反向删除（非空则保留）。因此「新建目录骨架 + 把文件归位」可以写在同一个 plan 里一次完成，不必先手动 `mkdir`。

新建骨架属于**方案变更**，必须在 Step 4 的确认表里单独列出（哪几条新建、为什么这个层级），不能夹在改名里蒙混过去。

## 7. 深度与批量

- `--depth N` 限制下探层数：第一轮建议给 `--depth 2` 只处理根层与项目层，确认结构后再加深。
- 单轮确认的条目上限 50 个文件（见 SKILL.md Step 3），目录改动**也计入**这个上限。
- 根目录选得太高（例如整个 `~/Documents`）会让第一层日期规则误伤所有既有项目目录：那是重建，不是整理。宁可先选一个项目目录跑通，再逐步扩大。
